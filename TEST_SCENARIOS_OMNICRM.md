**Проект:** omniCRM — омниканальная CRM-система  
**Дата:** 24 сентября 2026  
**Цель:** Оценка навыков тест-дизайна, понимания бизнес-логики и внимания к деталям

## 📋 О проекте omniCRM

**omniCRM** — это омниканальная CRM-система для управления клиентскими диалогами через множество каналов связи.

### Ключевые особенности

- **Мультиканальность:** Telegram, WhatsApp, VK, Instagram, MAX, веб-виджет
- **Единый интерфейс:** Операторы работают в одной панели, клиенты — через свои каналы
- **Роли:** Суперадмин, Админ, Оператор
- **Функционал:**
  - Диалоги 1-на-1 и групповые комнаты (до 150 клиентов + 50 операторов)
  - CRM-карточки клиентов и воронка продаж
  - Автоответы и боты
  - SLA и аналитика
  - Рассылки по сегментам
  - Прокси-менеджер для каналов
  - Внутренние комментарии и упоминания (@mention)

### Технический стек

- **Backend:** Python (FastAPI), PostgreSQL, Kafka
- **Frontend:** React, TypeScript
- **Инфраструктура:** Docker, Kubernetes, S3 (Garage), Proxy Manager
- **Интеграции:** Telegram Bot API, WhatsApp Business API, VK API, Instagram Graph API

## 🎯 СЦЕНАРИЙ 1: Тестирование групповых комнат (CMVP-137)

### Контекст задачи (Сценарий 1)

Реализуется функционал **групповых комнат** для совместного общения клиентов и операторов:

- Максимум **150 клиентов** + **50 операторов**
- У комнаты есть название, ответственный оператор
- Клиенты общаются через свои каналы (Telegram, WhatsApp и т.д.)
- Операторы — через CRM-панель
- Один клиентский диалог может быть подключён только к **одной активной комнате**

### Ваша задача (Сценарий 1)

**Составьте тест-кейсы для функционала создания и управления групповыми комнатами.**

#### Требования к тест-кейсам

1. **Создание комнаты:**
   - Валидация названия (мин/макс длина, спецсимволы)
   - Выбор участников (клиенты + операторы)
   - Назначение ответственного
   - Проверка лимитов (150 клиентов, 50 операторов)

2. **Приглашение клиентов:**
   - Приглашение существующего клиента из CRM
   - Приглашение нового клиента по контакту
   - Проверка дубликатов (клиент уже в другой активной комнате)
   - Статусы приглашений (отправлено, принято, отклонено, ошибка)

3. **Отправка сообщений:**
   - Сообщение от оператора → все клиенты получают в своих каналах
   - Сообщение от клиента → все участники видят в комнате
   - Вложения (изображения, файлы)
   - Порядок сообщений при одновременной отправке

4. **Граничные случаи:**
   - Попытка добавить 151-го клиента
   - Попытка добавить 51-го оператора
   - Клиент уже в активной комнате A, пытаемся добавить в комнату B
   - Удаление ответственного оператора из комнаты
   - Потеря соединения во время отправки сообщения

5. **Интеграции:**
   - Клиент в Telegram получает сообщение из комнаты
   - Клиент в WhatsApp отвечает в комнату
   - Клиент в VK выходит из комнаты
   - Разные клиенты в разных каналах одновременно пишут

### Критерии оценки (Сценарий 1)

- ✅ Полнота покрытия (позитивные + негативные + граничные)
- ✅ Структура тест-кейсов (предусловия, шаги, ожидаемый результат)
- ✅ Приоритизация (критичность)
- ✅ Понимание бизнес-логики и рисков
- ✅ Внимание к деталям (race conditions, асинхронность)

## 🎯 СЦЕНАРИЙ 2: Тестирование Proxy Manager (CMVP-138, CMVP-145)

### Контекст задачи (Сценарий 2)

**Proxy Manager** — централизованный сервис управления прокси для всех каналов:

- Общий пул прокси с параметрами: страна, тип сети, IP-версия, протокол
- Каждому аккаунту (Telegram, WhatsApp и т.д.) назначается подходящий прокси
- Прокси не меняется при капче, FloodWait, блокировке аккаунта
- Прокси **меняется** только при подтверждённой сетевой ошибке
- Логин/пароль прокси хранятся **зашифрованно**
- Один аккаунт = один прокси (не два одновременно)
- У каждого канала свой S3-бакет (изоляция)

### Ваша задача (Сценарий 2)

**Составьте тест-план для Proxy Manager API.**

#### Что нужно протестировать

1. **Импорт прокси:**
   - Загрузка списка прокси (формат: `protocol://login:password@host:port`)
   - Валидация формата
   - Дубликаты (обновление существующих)
   - Некорректные данные (невалидный IP, порт вне диапазона)

2. **Назначение прокси аккаунту:**
   - Запрос прокси для Telegram-аккаунта (страна: RU, тип: residential)
   - Повторный запрос от того же аккаунта → возвращает текущее назначение
   - Нет подходящих прокси в пуле → ошибка
   - Лимит аккаунтов на прокси исчерпан → выбирается другой

3. **Обработка ошибок:**
   - **Сетевая ошибка** (connection timeout) → прокси меняется
   - **Капча** от Telegram → прокси НЕ меняется
   - **FloodWait** (rate limit) → прокси НЕ меняется
   - **Блокировка аккаунта** → прокси НЕ меняется
   - **Ошибка авторизации** (неверный токен) → прокси НЕ меняется

4. **Безопасность:**
   - Логин/пароль прокси не попадают в логи
   - Логин/пароль не попадают в Kafka-сообщения
   - Админский токен короче 32 символов → отклоняется
   - Клиентский токен даёт доступ только к своим назначениям

5. **Изоляция каналов:**
   - Telegram-коннектор имеет доступ только к бакету `telegram`
   - WhatsApp-коннектор не может читать из бакета `telegram`
   - Проверка ACL в S3

6. **Heartbeat и освобождение:**
   - Аккаунт отправляет heartbeat каждые 60 секунд
   - Heartbeat не приходит 5 минут → назначение освобождается
   - Явное освобождение через DELETE `/assignments/{account_id}`

### Вопросы для анализа

1. Как протестировать, что прокси **не меняется** при капче, но **меняется** при сетевой ошибке?
2. Как проверить, что логин/пароль зашифрованы в БД?
3. Как протестировать race condition: два аккаунта одновременно запрашивают последний свободный прокси?
4. Как проверить, что presigned-ссылка на S3 протухла через 15 минут?

### Критерии оценки (Сценарий 2)

- ✅ Понимание логики принятия решений (когда менять прокси, когда нет)
- ✅ Тестирование безопасности (шифрование, изоляция)
- ✅ Асинхронные сценарии (heartbeat, retry, DLQ)
- ✅ Интеграционное тестирование (Kafka, S3, коннекторы)

## 🎯 СЦЕНАРИЙ 3: Тестирование рассылок по сегментам (CMVP-143)

### Контекст задачи (Сценарий 3)

Функционал **рассылок** позволяет отправлять сообщения клиентам по фильтрам:

- Фильтры: источник (канал), теги, стадия CRM, активность
- Перед запуском показывается количество получателей
- После запуска — ход рассылки, результаты доставки, ошибки
- **Запрещено** отправлять одному получателю дважды
- Рассылка не смешивается с массовыми действиями над диалогами

### Ваша задача (Сценарий 3)

**Составьте тест-кейсы для функционала рассылок.**

#### Требования

1. **Создание рассылки:**
   - Выбор сегмента (фильтры)
   - Предпросмотр количества получателей
   - Валидация текста сообщения (мин/макс длина)
   - Вложения (опционально)

2. **Фильтры:**
   - По источнику: только Telegram
   - По тегам: клиенты с тегом "VIP"
   - По стадии CRM: "Новый лид"
   - Комбинация фильтров: Telegram + VIP + Новый лид
   - Пустой результат фильтра → предупреждение

3. **Запуск рассылки:**
   - Отправка начинается
   - Прогресс: 50/100, 100/100
   - Результаты: доставлено, ошибка, не доставлено
   - Один клиент в сегменте дважды → получает только 1 сообщение

4. **Ограничения каналов:**
   - Telegram: лимит 30 сообщений/секунду
   - WhatsApp Business: лимит 1000 сообщений/день
   - Превышение лимита → рассылка приостанавливается

5. **Ошибки доставки:**
   - Клиент заблокировал бота → ошибка, продолжаем дальше
   - Канал недоступен → ошибка, продолжаем дальше
   - Сетевая ошибка → retry 3 раза, потом ошибка

6. **Отмена рассылки:**
   - Отмена во время выполнения
   - Уже отправленные сообщения не отзываются
   - Статус: "Отменена (50/100 отправлено)"

### Граничные случаи (Сценарий 3)

- Сегмент содержит 10 000 клиентов
- Клиент удалён из CRM во время рассылки
- Клиент изменил канал (был Telegram, стал WhatsApp) во время рассылки
- Два оператора запускают рассылку одновременно на один сегмент

### Критерии оценки (Сценарий 3)

- ✅ Понимание бизнес-логики (дедупликация, лимиты каналов)
- ✅ Обработка ошибок и retry-логики
- ✅ Тестирование производительности (10 000 клиентов)
- ✅ Race conditions (одновременные рассылки)

## 🎯 СЦЕНАРИЙ 4: Тестирование внутренних комментариев и @mentions (CMVP-141)

### Контекст задачи (Сценарий 4)

Операторы могут оставлять **внутренние комментарии** в диалоге:

- Комментарии видны только сотрудникам
- **Не отправляются** клиенту во внешний канал
- Можно упомянуть коллегу через `@username`
- Упомянутый сотрудник получает уведомление
- Доступ к комментариям определяется правами на диалог

### Ваша задача (Сценарий 4)

**Составьте тест-кейсы для внутренних комментариев.**

#### Требования (Сценарий 4)

1. **Создание комментария:**
   - Оператор пишет комментарий в диалоге
   - Комментарий сохраняется
   - Клиент **не видит** комментарий в своём канале (Telegram, WhatsApp)

2. **Упоминания (@mention):**
   - Ввод `@` → появляется список доступных сотрудников
   - Выбор сотрудника → вставляется `@username`
   - Упомянутый сотрудник получает уведомление
   - Упоминание несуществующего пользователя → ошибка или игнорируется

3. **Права доступа:**
   - Оператор A имеет доступ к диалогу → видит комментарии
   - Оператор B **не имеет** доступа → не видит комментарии
   - Админ видит все комментарии

4. **Визуальное отличие:**
   - Комментарии отличаются от обычных сообщений (цвет, иконка)
   - Показывается автор и время комментария

5. **Граничные случаи:**
   - Комментарий с 10 упоминаниями
   - Упоминание самого себя
   - Комментарий без текста (только упоминание)
   - Удаление упомянутого сотрудника из системы

### Интеграционные сценарии (Сценарий 4)

- Оператор пишет комментарий в диалоге с клиентом в Telegram
- Проверка: клиент в Telegram **не получает** сообщение
- Проверка: другой оператор в CRM **видит** комментарий
- Упомянутый оператор получает push-уведомление

### Критерии оценки (Сценарий 4)

- ✅ Понимание разницы между комментариями и сообщениями
- ✅ Тестирование прав доступа
- ✅ Проверка уведомлений
- ✅ Интеграционное тестирование (клиент не получает комментарий)

## 🎯 СЦЕНАРИЙ 5: Тестирование вложений (контракт 2.0, CMVP-146)

### Контекст задачи (Сценарий 5)

Вложения (изображения, файлы) передаются между CRM и коннекторами по **контракту 2.0**:

- **Старый контракт 1.1:** presigned-ссылка на S3 (живёт 15 минут)
- **Новый контракт 2.0:** указатель `bucket + key` (claim check pattern)
- У каждого канала свой S3-бакет (изоляция)
- Коннектор имеет доступ только к своему бакету
- Сообщение может лежать в `.retry` или `.dlq` часами

### Ваша задача (Сценарий 5)

**Составьте тест-план для миграции на контракт 2.0.**

#### Что нужно протестировать

1. **Загрузка вложения:**
   - Клиент отправляет изображение в Telegram
   - Telegram-коннектор загружает файл в бакет `telegram`
   - В Kafka публикуется событие с `bucket: "telegram", key: "path/to/file.jpg"`
   - CRM скачивает файл из S3

2. **Отправка вложения:**
   - Оператор отправляет файл клиенту в WhatsApp
   - CRM загружает файл в бакет `whatsapp`
   - WhatsApp-коннектор скачивает файл и отправляет клиенту

3. **Изоляция бакетов:**
   - Telegram-коннектор пытается прочитать из бакета `whatsapp` → 403 Forbidden
   - WhatsApp-коннектор пытается записать в бакет `telegram` → 403 Forbidden

4. **Протухшие ссылки (контракт 1.1):**
   - Сообщение с presigned-ссылкой лежит в `.retry` 20 минут
   - Попытка скачать файл → ссылка протухла → ошибка
   - **Контракт 2.0:** ссылка не протухает, т.к. это `bucket + key`

5. **Retry и DLQ:**
   - Сообщение с вложением попадает в `.retry` (временная ошибка)
   - Через 1 час сообщение обрабатывается → файл успешно скачивается
   - Сообщение в `.dlq` (постоянная ошибка) → файл всё ещё доступен

6. **Версия контракта:**
   - Сообщение с `contract_version: 2.0` обрабатывается корректно
   - Сообщение с `contract_version: 1.1` (старый формат) → fallback или ошибка?

### Вопросы для анализа (Сценарий 5)

1. Как протестировать, что presigned-ссылка протухла через 15 минут?
2. Как проверить, что Telegram-коннектор **не имеет** доступа к бакету WhatsApp?
3. Как эмулировать сообщение, лежащее в `.retry` 2 часа?
4. Как проверить обратную совместимость с контрактом 1.1?

### Критерии оценки (Сценарий 5)

- ✅ Понимание claim check pattern
- ✅ Тестирование изоляции (S3 ACL)
- ✅ Асинхронные сценарии (retry, DLQ, протухшие ссылки)
- ✅ Миграция и обратная совместимость
